### Bugs found

**Bug A — ffmpeg crashes on Windows (exit code 3199971767 = 0xBEBBB1B7)**
All HEIC import fails with `IMG_0982.HEIC — ffmpeg exited with code 3199971767`.
Affects both local folder import and Google Photos Picker import.
Root cause hypothesis: the GitHub Actions CI pipeline (Ubuntu runner) installs the Linux ELF
`ffmpeg-static` binary at `npm install` time. `electron-builder --win` then packages this Linux
binary into the Windows installer. `electron-builder`'s `npmRebuild: true` only rebuilds native
`.node` addons — it does not re-run `ffmpeg-static`'s post-install script for the target platform.

**Bug B — HEIC not detected as duplicates**
Photos already in the library reported as "collisions" (filename match) instead of "duplicates"
(pHash match). Caused by Bug A: ffmpeg fails silently in planner → `phashResult = null` →
pHash check skipped → file proceeds to filename collision check.

**Bug C — Silent failures, no user feedback**
When HEIC conversion fails, no warning is shown during indexing or analysis.

## HEIC tile grid investigation

### HEIC container structure
iPhone HEIC files use a **HEVC Tile Grid** structure:
- 48 independent 512×512 HEVC tiles (streams `#0:0` to `#0:47`, labeled `dependent`)
- 1 assembled tile grid at 3024×4032 (stream group `#0:0[0x31]`, labeled `default`)

### ffmpeg cannot assemble the tile grid
Without any filter, ffmpeg selects stream `#0:0` (first tile, 512×512) rather than assembling
the full tile grid, despite the grid being labeled `(default)`.

When forced with `-vf scale=3024:4032`, ffmpeg does NOT decode the full grid — it upscales
tile 0 to the target size. Confirmed by pixel fingerprint comparison: pixels of the
"full res" (scale=3024:4032, 3024×3024) are virtually identical to tile 0 (512×512),
and completely different from tile 23 (middle of the image).

### pHash from tile 0 ≠ full image pHash
The current production pHash (ffmpeg → tile 0, 512×512) only represents the top-left
2.2% of the image (512²/3024×4032). Cross-format deduplication (HEIC library vs JPEG
import) is broken: a proper full-resolution JPEG of the same photo would produce a
completely different pHash.

### Alternative approaches tested

| Approach | Result |
|---|---|
| ffmpeg → rawvideo pipe → dctHash (no temp file) | 158/158 different pHashes, slightly slower (52ms vs 41ms) — color space mismatch (Y channel vs RGB→gray) |
| ffmpeg → raw 512px gray pipe → sharp scale | 158/158 different pHashes — same root cause |
| ExifReader EXIF thumbnail | Not available: iPhone HEIC thumbnails are HEVC-encoded in the ISOBMFF container, not JPEG in EXIF APP1 |

### pHash algorithm is bound to the JPEG intermediate
The JPEG intermediate step (ffmpeg → JPEG → sharp) is not an implementation detail — it is
implicitly part of the hash algorithm due to the YUV→RGB→gray color space conversion chain.
Changing to rawvideo would produce incompatible hashes and invalidate all existing DB records.

### Performance benchmarks (5 HEIC files, ~12MP iPhone)
- ffmpeg → tile 0 (512×512, current): **41ms/file**
- ffmpeg → scale=512:512 explicit: **42ms/file** (identical result)
- ffmpeg → scale=3024:4032 (still tile 0, just upscaled): **102ms/file**

## Spec change decided

- Remove `heicConversion.enabled` boolean
- Replace with `heic.mode: 'keep' | 'convert'`, default `'keep'` (copy HEIC as-is)
- HEIC→JPEG conversion option stays available but requires a proper full-res decoder
  (ffmpeg cannot do this — tile grid assembly not supported)
- pHash computation always uses the current approach (ffmpeg → temp JPEG → sharp)

## Open questions / carry-over

- **HEIC full-image pHash**: cross-format dedup (HEIC vs JPEG) is broken with the current
  tile-based approach. The only known solution is a full HEIC decoder (heic-decode WASM ~2-5s,
  or a faster alternative). Decision deferred to TASK-039 design phase.
- **heic-decode WASM performance**: was measured at ~2-5s/file (full 12MP decode). If acceptable
  for batch indexing, could be reinstated just for pHash (not for conversion).
- User to review `/tmp/heic-inspection/` images visually to confirm tile 0 vs full image behavior.
