# Session 044 — 2026-03-07

## Task

**TASK-046-perf** — Native HEIC decoding via libheif N-API + worker pool

## Summary

Replaced the WASM-based HEIC decoder (`heic-decode`) with a native N-API addon (`libheif-node-dy`)
and added a `HeicDecodePool` for true CPU parallelism via `worker_threads`.

### Changes

| File | Change |
|------|--------|
| `src/main/heic-pool.ts` | **New** — HeicDecodePool class (create N workers, round-robin dispatch, terminate) |
| `src/workers/heic-decode.worker.ts` | **New** — Worker that loads libheif-node-dy, decodes HEIC buffers, returns RGBA via transferList |
| `src/main/heic.ts` | Replaced `heic-decode` (WASM) with `libheif-node-dy` (native N-API) in `defaultHeicDecode` |
| `src/workers/indexer.worker.ts` | Creates HeicDecodePool, injects pooled decode via `createUniversalPhashComputer` |
| `src/workers/planner.worker.ts` | Creates HeicDecodePool, injects pooled decode via `createUniversalPhashComputer` + `createHeicConverter` |
| `src/workers/importer.worker.ts` | Creates HeicDecodePool, injects pooled decode via `createHeicConverter` |
| `electron.vite.config.ts` | Added `heic-decode.worker` to rollup inputs |

| `.github/workflows/ci.yml` | Added `libheif-dev` to system dependencies |
| `tests/main/heic-pool.test.ts` | **New** — 12 tests for HeicDecodePool |

### Architecture

- `HeicDecodePool` creates N worker_threads, each loading `libheif-node-dy` independently
- Pool is created inside each operation worker (indexer, planner, executor) — nested workers
- Pool's `decode(buffer)` is compatible with `HeicDecodeFn` — zero changes to core processing logic
- Input HEIC buffers (~5 MB) are copied via structured clone; output RGBA (~46 MB) via transferList (zero-copy)
- Pool is terminated after each operation completes

### Performance

| Scenario | Before (WASM) | After (N-API pool) | Speedup |
|----------|---------------|---------------------|---------|
| 1 HEIC file | ~463 ms | ~282 ms | 1.6x |
| 10 HEIC files | ~4660 ms | ~370 ms | 12.6x |
